# 0003. 平台差异只在该平台修正

状态：已采纳
日期：2026-11-17

## 背景

`apps/remote` 的后端同时跑在 macOS / Linux / Windows。一批测试长期只在类 Unix 上跑，
于是 Windows 上积累了四类真实缺陷：

- 会话 ID 形如 `codex-thread:<uuid>`，其中的 `:` 是 Windows 非法文件名字符
- 打开目录句柄做 `Sync()`（fsync）在 Windows 返回 `Access is denied`
- 用 rename 覆盖一个仍被打开的文件，Windows 拒绝（POSIX 允许）
- 时间轴附件只识别 `/` 开头的路径，`C:\…` 认不出来

修的时候面临一个选择：**全平台统一改**，还是**只在该平台改**。

## 选项

1. **全平台统一行为**（例如所有平台都编码文件名）：行为一致、跨平台同步数据目录时不分裂；
   代价是改变磁盘布局，macOS/Linux 上已有用户的会话文件名需要迁移，迁移本身有风险。
2. **只在该平台修正**：Windows 上把 `:` 转义为 `%3A`、跳过目录 fsync、调整 rename 顺序；
   macOS / Linux 保持原状，用户零迁移。

## 结论

选 2。**只在有问题的平台修正，不动其他平台的行为。**

- 文件名编码：`runtime.GOOS == "windows"` 时才把 `:` 换成 `%3A`
- 目录 fsync：Windows 上退化为 no-op（NTFS 的重命名本身是原子的）
- rename 覆盖：改为先关闭所有句柄再替换（这是正确的，全平台都受益）
- 权限断言：Windows 没有 POSIX 权限位，测试按平台跳过

## 后果

- 老用户无迁移成本，风险最小。
- 代价：**跨平台同步数据目录时文件名可能分裂**（macOS 的 `codex-thread:x.json` 在 Windows 上
  对应 `codex-thread%3Ax.json`）。当前实现里会话镜像本来就按本机状态重建，不要求跨平台
  复用磁盘文件，所以这个代价可接受。
- 约束：以后任何"平台差异"都必须先问一句——**这个差异是真的平台限制，还是我们没写对？**
  rename 那条就属于后者（先关闭再替换是普遍正确的），所以全平台都改了。
